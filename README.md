# Team Task Manager

[![CI](https://github.com/lumen-dev02/team-task-manager/actions/workflows/ci.yml/badge.svg)](https://github.com/lumen-dev02/team-task-manager/actions/workflows/ci.yml)

API для совместной работы над задачами. Пользователь создаёт проект, добавляет участников и назначает им задачи. У задач есть статусы и история изменений, у проекта — владелец и команда.

Это самый большой из моих учебных проектов, основа для курсовой. Здесь я разбираю не только CRUD, но и ситуации на стыке прав доступа и транзакций: например, что делать, если участника удаляют из команды в тот момент, когда ему назначают задачу.

## Что работает

- Регистрация, вход и JWT access-токен на один час.
- Создание, просмотр и удаление проектов; список только своих проектов.
- Две роли: владелец и участник. Только владелец управляет составом команды и удаляет проект.
- Создание, чтение, полное обновление и удаление задач участниками проекта.
- Статусы `todo`, `in_progress`, `done`; исполнитель из числа участников или `null`.
- Фильтрация задач по статусу и исполнителю, пагинация списков проектов, задач и истории.
- История создания и смены статусов с автором и временем изменения.
- Проверка версии при обновлении задачи: устаревшая правка получает `409 Conflict`.
- При удалении участника его задачи сохраняются, исполнитель снимается, версия увеличивается.

## Стек

Go 1.26+, стандартный `net/http`, PostgreSQL 17, `pgx/v5`, `golang-jwt/jwt/v5` и bcrypt. SQL написан вручную. Для локального запуска приложения и базы есть Docker Compose.

## Быстрый запуск

Нужны Git, Docker с Compose v2 и OpenSSL. Go для запуска через Docker не требуется.

```bash
git clone https://github.com/lumen-dev02/team-task-manager.git
cd team-task-manager
cp .env.example .env
openssl rand -hex 32
```

Вставьте результат последней команды в `JWT_SECRET` в `.env`: с шаблонным секретом приложение не запустится. Пароль PostgreSQL из примера оставляйте только для локальной разработки. Если меняете его, удобно взять hex-строку, чтобы не экранировать символы в URL подключения.

```bash
docker compose up --build -d
docker compose ps -a
curl --fail http://localhost:8080/readyz
```

Сначала Compose поднимает БД, затем применяет миграцию и запускает API. Контейнер `migrate` после работы должен быть в состоянии `Exited (0)` — это нормально. База доступна на `127.0.0.1:55432`, API — на `127.0.0.1:8080`. Порты можно изменить в `.env`.

```bash
docker compose logs api migrate
docker compose down
```

`down` останавливает контейнеры, но сохраняет данные. Не добавляйте `-v`, если база ещё нужна: этот флаг удаляет volume вместе с данными проекта.

### Без Docker для приложения

Нужны Go 1.26+ и запущенный PostgreSQL. Базу можно поднять отдельно:

```bash
docker compose up -d --wait db
export DATABASE_URL='postgres://taskmanager:local-development-only@localhost:55432/taskmanager?sslmode=disable'
export JWT_SECRET="$(openssl rand -hex 32)"
go run ./cmd/api -migrate
go run ./cmd/api
```

URL выше соответствует исходному `.env.example`; если меняли пароль или порт, обновите его. При запуске через Go приложение само не читает `.env`, нужны переменные окружения. Адрес сервера задаётся через `HTTP_ADDR`, по умолчанию `:8080`.

## Пример API

```bash
curl --fail-with-body -sS http://localhost:8080/api/v1/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"timur@example.com","name":"Timur","password":"local-demo-password"}'

curl --fail-with-body -sS http://localhost:8080/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"timur@example.com","password":"local-demo-password"}'
```

Скопируйте `access_token` из ответа входа:

```bash
export TOKEN='<access_token>'
curl --fail-with-body -sS http://localhost:8080/api/v1/projects \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"Course project","description":"Team planning"}'

# Подставьте id проекта из ответа вместо 1.
curl --fail-with-body -sS http://localhost:8080/api/v1/projects/1/tasks \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"title":"Describe the API"}'
```

Полный повторяемый сценарий с двумя пользователями, назначением исполнителя, сменой статуса и удалением участника:

```bash
# Дополнительно нужны curl, jq и openssl. API должен быть запущен.
bash scripts/demo.sh
# Для другого порта: BASE_URL=http://localhost:8081 bash scripts/demo.sh
```

Скрипт создаёт тестовые аккаунты и оставляет демонстрационный проект в БД. Токены в терминал не выводятся. Остальные запросы, права и ошибки собраны в [справочнике API](docs/api.md).

## Тесты и проверки

```bash
go test -race -count=1 ./...
go vet ./...
go build ./cmd/api
```

Без `TEST_DATABASE_URL` интеграционные тесты пропускаются. Для проверки с настоящей БД:

```bash
docker compose up -d --wait db
export TEST_DATABASE_URL='postgres://taskmanager:local-development-only@localhost:55432/taskmanager?sslmode=disable'
go test -race -count=1 ./... -v
# Или только интеграционные:
make test-integration
```

Пользователю PostgreSQL нужно право `CREATE SCHEMA`. Каждый интеграционный тест работает в своей схеме и удаляет её после выполнения. Таблицы приложения не очищаются, но для тестов всё равно лучше выделить отдельную БД.

В тестах есть обычные сценарии — регистрация, вход, задачи, фильтры — и несколько менее очевидных: доступ к чужому проекту, два обновления одной версии задачи, удаление участника одновременно с назначением. Отдельно проверяются JWT, валидация и повторное применение миграции. GitHub Actions поднимает PostgreSQL, запускает тесты с race detector, `go vet` и собирает контейнер.

## Структура

```text
cmd/api/            точка входа, запуск миграций, graceful shutdown
internal/auth/      bcrypt и JWT
internal/config/    конфигурация из окружения
internal/domain/    модели и ошибки
internal/httpapi/   маршруты, middleware, валидация, HTTP-тесты
internal/store/     SQL, транзакции и проектные права доступа
migrations/        встроенная начальная SQL-миграция и её запуск
docs/              контракт API и архитектурные решения
scripts/           демонстрационный сценарий
```

### Несколько решений

Обработчики разбирают запросы и возвращают HTTP-ответы, а права доступа и транзакции находятся в `store`. Отдельный сервисный слой пока не выделял: большинство правил здесь тесно связано с SQL.

При изменении задачи клиент передаёт её `version`. Если кто-то уже успел сохранить новую версию, API отвечает `409`, а не молча затирает изменения. Обновление задачи и запись истории статуса выполняются в одной транзакции.

Операции внутри проекта берут блокировку строки проекта, в том числе при чтении. Так проще не допустить гонку между проверкой членства и изменением данных. Цена решения — запросы одного проекта выполняются последовательно. Для небольшой команды это допустимое упрощение, но под высокую нагрузку блокировки пришлось бы пересмотреть.

Подробности модели данных, JWT и миграции — в [описании архитектуры](docs/architecture.md).

## Что пока не сделано

- Нет веб-интерфейса, уведомлений, дедлайнов, вложений и поиска.
- Участник добавляется владельцем сразу по email. Приглашений с подтверждением и проверки почты нет.
- JWT действует час; refresh-токенов, отзыва токенов и восстановления пароля пока нет. Передать владение проектом тоже нельзя.
- История удаляется вместе с задачей или проектом. Она нужна для просмотра изменений, а не для неизменяемого аудита.
- Лимит входа и регистрации общий на весь процесс: 2 запроса в секунду, burst 5. Он ограничивает затраты на bcrypt, но не различает клиентов.
- Runner умеет применять только начальную миграцию. Для изменения схемы нужно добавить следующий версионный шаг или перейти на готовый инструмент, а не редактировать уже применённый SQL.

Compose настроен для локальной работы. Перед публикацией сервиса нужны как минимум HTTPS, отдельные секреты, резервные копии и более точные ограничения запросов.
