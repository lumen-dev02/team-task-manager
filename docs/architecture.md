# Архитектура и решения

## Поток запроса

```text
net/http → request ID / logging / timeout / recovery
         → JWT authentication
         → handler: JSON и валидация
         → store: проектные права и SQL-транзакция
         → PostgreSQL
```

Один процесс API, одна PostgreSQL. `net/http` достаточно для маршрутов с параметрами, отдельный фреймворк не нужен. SQL написан вручную: так видны выборки, индексы и границы транзакций. Типы ошибок домена отделяют ожидаемые ситуации от внутренних ошибок БД; HTTP-слой выбирает статус ответа, детали SQL остаются в логах.

Сервисный слой и интерфейс репозитория сейчас не выделены: самостоятельных внешних интеграций и сложной оркестрации нет. Если появятся уведомления или другие хранилища, эти границы стоит пересмотреть. Текущие SQL-операции проверяются на PostgreSQL, а не на моках, которые не воспроизводят ограничения и блокировки.

## Модель данных

```text
users ──< project_members >── projects
  │                              │
  └── created_by / changed_by     └──< tasks ──< task_status_history
```

- Владелец задан `projects.owner_id` и одновременно записан в `project_members`. Отдельного изменяемого поля роли нет: роль вычисляется по владельцу, два источника истины не расходятся.
- Составной FK `(project_id, assignee_id)` запрещает назначение пользователя, не входящего в проект. Приложение дополнительно проверяет условие, чтобы вернуть понятную клиентскую ошибку.
- Удаление проекта каскадно удаляет участников, задачи и историю. Автор задачи сохраняется после исключения из команды, поскольку ссылается на `users`, а не на членство.
- Индексы поддерживают поиск проектов пользователя, выборки задач по проекту/статусу/исполнителю и историю по задаче. Гарантий производительности без измерений нет.
- `version` — счётчик изменений, а не timestamp. Он не зависит от точности времени или совпадения часов клиентов.

## Транзакции и права

Любая операция внутри проекта, включая чтение, использует `store.inProject`:

1. Начать транзакцию, поставить локальный `statement_timeout` 5 секунд.
2. Заблокировать строку проекта через `SELECT ... FOR UPDATE`.
3. Проверить членство, при необходимости — владельца.
4. Выполнить операцию и зафиксировать транзакцию.

Почему так: проверка прав вне транзакции оставила бы окно между проверкой членства и изменением задачи. Единая блокировка устраняет гонку удаления участника с назначением задачи, не требует нескольких несовместимых порядков блокировок. Если удаление участника завершилось первым, назначение отклоняется; если назначение было первым, удаление снимает исполнителя в той же транзакции.

Цена — операции одного проекта сериализуются. Это осознанное упрощение для небольшого учебного API, а не высоконагруженная архитектура. При росте нагрузки можно разделить режимы блокировок чтения/записи и использовать условные UPDATE по версии, но для этого нужны дополнительные конкурентные тесты. Список проектов пользователя выполняется одним SQL-запросом без этой блокировки.

Создание проекта и добавление владельца атомарны. Создание задачи и начальное событие истории атомарны. Обновление задачи и событие смены статуса также атомарны: ошибки откатывают оба изменения. Текущая версия проверяется под блокировкой проекта, поэтому из двух конкурентных PUT с одной версией проходит только один.

При удалении участника сначала снимается назначение с его задач с увеличением их версий, затем удаляется членство. Владелец не может исключить себя. Других маршрутов изменения владельца и членства нет. Эти правила защищают API; обладатель прямого SQL-доступа к БД не ограничивается прикладными проверками.

## Аутентификация и безопасность

- Пароли хешируются bcrypt с cost 12, не сохраняются и не логируются в открытом виде. Максимум 72 байта проверяется до вызова bcrypt.
- Для отсутствующего пользователя вход выполняет сравнение с заранее созданным bcrypt-хешем. Это сближает стоимость неверных попыток, но не является гарантией полного отсутствия timing side channels.
- JWT живёт час. Разрешён только HS256; проверяются подпись, issuer, audience, обязательный `exp`, положительный ID в `sub`.
- Секрет минимум 32 байта, демонстрационное значение из `.env.example` отклоняется. Реальная энтропия зависит от генерации секрета; проверка длины её не доказывает.
- Токен не хранит роли: права перечитываются из БД на каждом проектном запросе. Исключённый участник теряет доступ сразу, даже если JWT ещё не истёк.
- SQL параметризован. JSON ограничен по размеру, неизвестные поля запрещены; строки, сохраняемые в PostgreSQL TEXT, не принимают NUL.
- Общий rate limiter защищает auth-эндпоинты от неограниченного потока вычислений bcrypt. Лимит локален процессу, не различает клиентов и сбрасывается при рестарте.
- CORS не включён, cookie-аутентификации нет. Токены нужно хранить на стороне клиента безопасно; API рассчитан на Bearer-заголовок.
- Compose публикует порты только на loopback. Контейнер API работает не от root. HTTPS и управление секретами для публичной среды остаются задачами развёртывания.

## Миграция и эксплуатация

`go run ./cmd/api -migrate` использует встроенный через `go:embed` файл `001_init.sql`. В одной транзакции берётся advisory lock, создаётся таблица `schema_migrations`, проверяется SHA-256 файла и применяется начальная схема. Повторный запуск не меняет данные. Изменение уже применённого SQL вызывает ошибку checksum.

Это минимальный runner **одной начальной миграции**, не универсальная система версионирования. Down-команды нет. Для следующего изменения схемы нужно добавить новый версионный шаг и расширить runner либо перейти на готовый инструмент, сохранив сведения о применённой схеме. Нельзя просто переписывать `001_init.sql` в существующей БД.

API самостоятельно схему не меняет. В Compose есть одноразовый migration job, успешного завершения которого ждёт API. В окружении вне Compose порядок миграции и запуска обеспечивает оператор.

У HTTP-сервера ограничены заголовки и времена чтения, записи и простоя. У запроса есть контекст на 10 секунд; readiness использует отдельный секундный таймаут. Контекст ограничивает запросы к БД, но не прерывает уже начавшееся вычисление bcrypt. Пул — максимум 10 соединений. При SIGINT/SIGTERM сервер до 15 секунд ждёт текущие запросы, затем закрывается. Логи JSON содержат метод, путь без query string, статус, время и request ID; тела и Authorization не пишутся.

## Что проверяют тесты

Unit-тесты проверяют конфигурацию, хеширование, валидность и отрицательные случаи JWT, разбор JSON, пагинацию, валидацию и middleware. Интеграционные HTTP-тесты используют настоящий store и PostgreSQL в изолированной схеме. Отдельные конкурентные сценарии проверяют устаревшую версию и удаление участника одновременно с назначением задачи.

Race detector обнаруживает гонки памяти Go; корректность SQL-конкурентности проверяют отдельные утверждения интеграционных тестов. Нагрузочное тестирование, проверка восстановления из резервных копий и аудит безопасности не проводятся и не заявляются.
